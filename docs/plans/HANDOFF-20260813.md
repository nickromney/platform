## The one thing left mid-investigation: section 4 (gitea)

This is where to pick up. The investigation advanced a long way but the fix is
**not** confirmed, and the working tree contains a change that does not yet work.

### What is now established

`dl.gitea.io` issues a redirect to `dl.gitea.com`. The host follows it fine
(`curl -L` reports `url_effective: https://dl.gitea.com/charts/index.yaml`,
200 in 0.32s). Inside the repo-server pod, `helm repo add` fails after 121s with:

```text
Get "https://dl.gitea.com/charts/index.yaml": context deadline exceeded
```

Note the host in that error is `dl.gitea.com`, not the `.io` name that was
requested. That detail is what the earlier round of investigation was missing.

`argocd-repo-server-helm-egress` (a CiliumClusterwideNetworkPolicy in
`terraform/kubernetes/cluster-policies/cilium/shared/argocd-hardened.yaml`)
allowlists `toFQDNs: dl.gitea.io` only. DNS resolves inside the pod for both
names, because the policy has a permissive L7 DNS rule.

### What was tried, and why it is not the answer yet

The working tree adds `matchName: dl.gitea.com` to that policy. **This did not
fix it.** After server-side applying the change and confirming both names were
live in the CCNP, the fetch still timed out at exactly 121s.

So the missing FQDN is real and the allowlist should almost certainly include
the redirect target regardless, but it is **necessary-not-sufficient** or the
root cause is elsewhere. Do not assume the edit in the tree is correct; it is an
unverified hypothesis.

### The strongest remaining lead

Cilium's FQDN cache appeared to hold nothing for either name:

```shell
kubectl -n kube-system exec <cilium-pod> -c cilium-agent -- \
  cilium-dbg fqdn cache list | grep -i gitea   # returned nothing
```

A `toFQDNs` policy only permits IPs that Cilium learned by observing a DNS
response through its proxy. If the agent is not caching these lookups, the
allowlist can name the host correctly and still permit no addresses, which
would present exactly as this timeout. Verify that first, before anything else.

Also worth checking: whether `dl.gitea.com` resolves to a different IP set
inside the pod than the one the policy learned (the pod saw `172.67.75.17`, the
host saw an IPv6 address), and Cilium drop counts for the repo-server endpoint
(`cilium-dbg monitor --type drop` while the fetch runs) to confirm the drop is
policy-driven at all rather than a cache or proxy problem in the image.

### Gotcha that will waste time otherwise

These policies are GitOps-managed. A plain `kubectl apply` silently reverts,
because the `cilium-policies` Argo Application has `selfHeal: true`, and a
client-side apply does not update `toFQDNs` at all when Argo owns the field via
ServerSideApply. To test live you must:

```shell
kubectl -n argocd patch applications.argoproj.io cilium-policies --type merge \
  -p '{"spec":{"syncPolicy":{"automated":null}}}'
kubectl apply --server-side --force-conflicts -f <policy file>
# ... test ...
kubectl -n argocd patch applications.argoproj.io cilium-policies --type merge \
  -p '{"spec":{"syncPolicy":{"automated":{"prune":true,"selfHeal":true}}}}'
```

**Auto-sync has been restored**; the cluster is not left paused. The real change
still has to go through `sync-gitea-policies.sh` to reach the Gitea repo.
